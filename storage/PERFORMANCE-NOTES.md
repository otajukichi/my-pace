# Local protocol IO performance work

This is synthetic simulator evidence only. No live Drive latency, quotas, source data, upload, deployment, authorization changes, or source writes are involved. The owner scheduler holds one bounded script-lock phase and uses the positive-read mode described below. Measurements count external service calls including retries, not merely parser steps. Final cold verification reads and initial bootstrap calls are excluded from the importer request total; file totals include the bootstrap.

## Changes

- `GasStoreIO` has an opt-in LRU positive protocol-read cache, limited to 512 retained files / 8 MiB by default. Both limits are independently enforced, with hard maxima of 1,024 files / 8 MiB. Files larger than the total byte cap remain uncached.
- `protocolReadCache: true` selects byte-only caching: every read still checks fresh ownership, private status, exact parent, markers and size. Cached bytes require matching valid Drive version and MD5 evidence. Missing or malformed evidence prevents caching.
- `protocolReadCache: {mode: 'lock-phase'}` also retains the verified positive protocol metadata during one continuously held runtime-owned lock. This is the explicit owner scheduler choice. It is a bounded trust interval, not repeated detection of external edits: a user or other program changing/deleting/sharing an already verified protocol file during that same phase may not be observed until the next phase. Every new runtime-owned acquisition revalidates. Protocol objects must remain immutable and server internal; the writer checks identity, hash and canonical form for each newly trusted protocol object, and references/transitions for each newly observed frame. The warm prefix described below is not re-decoded or revalidated on each use.
- Missing slots/successors are never cached. Source metadata, managed asset metadata/media and destination-parent privacy are never included. Immutable-create results do not seed the cache; attempting a create invalidates that ID so readback observes the actual winner.
- Runtime/coordinator lock acquisition and release use one facade. All retained bytes are cleared on release, exception, failed acquisition or observed loss of ownership. A caller's externally acquired raw lock never activates the cache because the runtime cannot observe its lifecycle. Trusted callers must not release/reacquire the underlying raw lock behind the facade during an active runtime operation.
- Multi-key radix updates now write each touched subtree once. Receipt key and revision-proof updates are also grouped. The existing copy-on-write transition verifier and immutable frame publication boundary are unchanged. Failed creates may still leave normal uncommitted staging; successful batches no longer leave their own intermediate index roots.
- The writer's leaf-entry ceiling is now 512, still bounded by the same 256 KiB encoded node ceiling. Existing smaller leaves remain readable. The default is global so runtime, bootstrap inspection and all new readers agree. The automatic checkpoint interval is 16 frames; runtime construction can supply explicit trusted writer limits, including a shorter interval for another internal service. Old copies of the implementation with a 16-entry reader limit must be replaced together before these new files are produced. No deployed upgrade is asserted.

- In full lock-phase mode, an opaque IO phase token also permits the writer to retain its already verified recovery prefix. Every recovery still freshly polls both reserved successor IDs. A newly visible checkpoint index forces full index/cut validation, including mandatory publishing-frame checks; a late frame is applied through the original transition verifier. New phase, failed recovery, failed publication or observed lock loss invalidates warm trust. Minimum acknowledgements remain checked. Checkpoint publication resets the logical replay span, while a separate per-recovery frame cap and a seeded/incremented index-link count preserve the original absolute recovery bounds.

Final configuration: 512-entry / 256 KiB leaf bounds, automatic checkpoint every 16 frames, 1 MiB source-range ceiling, one final quiescent checkpoint, bounded warm recovery, and owner work/closing deadlines of 105 / 120 seconds. Initial bootstrap requests and final verification are not charged to the importer totals below. All completed imports are independently reopened cold and checked for the full sample count. Original source writes: zero.

- One row: 296 importer requests, one invocation, 24-request completed cold recovery.
- Dense short-row 1 MiB: 1,048,596 bytes / 41,942 samples, 792 requests, one invocation, 24-request completed cold recovery.
- Representative 21-column sensor 1 MiB: 1,048,591 bytes / 5,065 samples, 432 requests, one invocation, 24-request completed cold recovery.
- Representative 31 MiB: 32,505,967 bytes / 157,033 samples, 4,966 requests, three cold invocations, no rolling-window wait. Request counts were 1,846 / 2,000 / 1,120. One call-cap yield resumed safely. Final cold recovery/read required 34 requests and about 76 ms local CPU. The entire local run took about 18.2 seconds, with zero simulated network latency; that is not a live completion-time estimate.

The 31 MiB zero-latency run retained 493 managed files: one bootstrap, 171 index nodes, 89 frames, 156 normalized outputs, 32 manifests, 32 parser checkpoints, six checkpoint manifests and six checkpoint-index links. The metadata history remains retained; no total-storage bound or garbage collection is claimed.

Explicit service-delay models for the same 31 MiB workload and unchanged hard limits:

- 100 ms per request: 5,494 actual requests, six cold invocations, 6,944 conservatively reserved requests in the ledger, no rolling-window wait. Maximum modeled invocation duration: 106.4 seconds. Final cold recovery: 34 requests. All five retry/error-state writes persisted, and all 157,033 samples were published.
- 300 ms per request: 7,152 actual requests, 20 cold invocations, 11,927 conservatively reserved requests, no rolling-window wait. Maximum modeled invocation duration: 114.9 seconds. Both models remained below the 16,000 rolling request allowance and 120-second hard invocation limit, including closing writes. Both retained the same 156 normalized outputs, so retries did not multiply imported output assets. These model totals are not a promise about real latency, invocation availability, user resumption cadence, or Apps Script quota classification. The harness inserts a fixed 100-second virtual gap between resumes; its virtual elapsed time is not an ETA.

Small default-suite regression ceilings are 400 / 1,100 / 550 importer requests for the one-row / dense-1-MiB / sensor-1-MiB cases, plus at most 40 requests for their completed cold recovery. These give roughly 25–40% headroom over the measured counts. The heavier 31 MiB and service-delay models are a separate explicit benchmark, not part of each ordinary test run.

## Scaling components, not a linear latency claim

For a source of S bytes and range ceiling B, the number of source checkpoints is R = ceil(S / B). Each range emits its own bounded output files, so total output-file count is the sum of per-range counts rather than simply ceil(total samples / 1,024). The 256 KiB output-byte ceiling can also force a flush before 1,024 samples; each prepared range remains limited to 64 outputs and 8 MiB total output.

External requests comprise fixed scan/register/publish work; current-source checks; per-range reservation and commit transactions; output/manifest/checkpoint creation and verified readback; grouped final verification; automatic and final checkpoints; cold recovery for each new invocation; closing ledger writes; and any failed-call retries. Each new protocol object requires its fresh parent check, immutable create, metadata check and bounded media readback on the ordinary no-retry path, before ID-allocation and tail polling costs. A transaction's index cost depends on the touched radix subtrees and encoded node sizes, not merely its number of entity changes.

Consequently the 31 MiB observed average, about 160 importer requests per MiB in the zero-latency model, is not a general linear bound. Wider rows, dense rows, byte-driven node splits, source changes, repeated interruption, cold history length, and different metadata/asset distributions change the cost. The package establishes safe resumption and modeled budget compliance for the stated fixtures; live timing remains an acceptance gate.

## Authenticated fixed-ID checkpoint acceleration (local candidate)

The cold-history path now optionally starts at an authenticated checkpoint hint. A new production bootstrap reserves a seventh, distinct `checkpointHintId` before any Drive creates and pins it in both its existing immutable configuration property and the bootstrap anchor. Legacy six-ID configurations and anchors remain valid, byte-for-byte unchanged; this implementation does not retrofit, reset, adopt, or silently migrate them. They retain full anchor recovery. Secret configuration alone does not add a hint pin to an older store.

`checkpoint-hint.mjs` requires a real HMAC-SHA256 callback. The GAS binding uses `Utilities.computeHmacSha256Signature` with explicit UTF-8 and the manually configured existing `MYPACE_WRITER_SECRET` (32–4,096 UTF-8 bytes). There is no unsigned, plain-digest, generated, or empty-secret fallback. No secret is put in Drive, returned, or logged. Authentication uses a dedicated `MyPace/Drive/checkpoint-hint/HMAC-SHA256/v1` domain. The canonical bounded envelope binds the anchor ID/hash, fixed hint ID, store ID, actual writer script ID, schema/dataset generation, immutable checkpoint-index ID/hash, and its absolute checkpoint ordinal.

The hint is advisory acceleration, never the source of committed state. Recovery always reads and validates the fixed bootstrap first. A missing, malformed, foreign, unauthenticated, or unreadable hint may fall back to the original anchor chain. Once a correctly authenticated, identity-matching hint selects a committed reference, missing/corrupt index, manifest or publishing-frame data fails closed; it cannot silently fall back to an older prefix. The hinted publishing frame is checked by the original frame/publication verifier before successor scanning. Subsequent index links and frame tails retain their original order, mandatory index barrier, receipt replay, epoch, version and minimum-acknowledgement checks. Referenced state/receipt shards remain lazily verified, as before. Retired cut-frame bodies are not reintroduced as a recovery dependency.

`GasStoreIO` exposes only `readCheckpointHint()` and `writeCheckpointHint(bytes)` for this mutable object, with no caller-selected ID, role, parent or metadata arguments. Reads and writes freshly enforce the fixed private metadata parent, ownership, untrashed state, MIME, exact single parent and hint/store role markers. Hint media is never entered in the immutable-read cache. A checkpoint publishes its immutable frame and mandatory checkpoint index before attempting one bounded same-ID hint create/update. No failed or ambiguous hint write retries with a new ID, changes the authoritative commit or creates an empty store. Scheduled IO meters the update call along with creates and reads. The binding uses the documented Advanced Drive `Files.update(resource, fileId, media, options)` method; it does not use DriveApp or broaden scopes. Official API references: [Advanced Drive service](https://developers.google.com/apps-script/advanced/drive), [files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update), and [Utilities HMAC](https://developers.google.com/apps-script/reference/utilities).

Delayed mutable updates may regress the hint. A stale but valid hint still follows the durable successor index/frame chain to the latest available committed state. HMAC establishes who issued a reference, not that the reference is the latest. If every piece of evidence of a newer commit disappears (including successors and every retained acknowledgement), no hint or anchor-only reader can infer that lost history. Supplied minimum acknowledgements still force failure when their revision/hash cannot be proved. The hint is not a trusted monotonic head and does not remove this lost-all-evidence limitation.

The absolute 4,096-checkpoint maintenance ceiling remains enforced, including after a hint shortcut, using the authenticated ordinal. It is not reinterpreted as merely a suffix limit. Losing the hint or changing/removing its key therefore does not introduce a new unbounded recovery requirement; the original explicit recovery bound still applies. Retained history, receipts and staging continue to grow overall; retention/GC and incremental maintenance are separate unfinished work. The shortcut improves cold startup within those existing bounds, not store lifetime or total-storage boundedness.

`checkpoint-hint.test.mjs` and independent `hint-review.test.mjs` cover domain separation, signed-byte GAS HMAC, malformed and forged envelopes, fixed-ID update semantics, role/privacy checks, absent keys and key rotation, legacy bootstrap preservation, stale/regressed hints, missing/corrupt authenticated targets, mandatory publication interruption, original receipt and acknowledgement proofs, long-history cold read budgets, and the unchanged absolute maintenance bound. These are local simulations, not measurements of live Google latency or consistency.

### Scheduled 31 MiB hint-enabled model

`scheduled-performance-hint-results.jsonl` records the independent complete scheduled-boundary models using the new pinned/authenticated hints, checkpoint interval 4, bounded 60-second scheduled slices, and a fresh runtime on every tick. Both independently reopened the completed job and checked all 157,033 samples from the 32,505,967-byte synthetic 21-column source, with zero original-source writes:

- 100 ms per external service call: 23 cold ticks, 7,530 actual requests, maximum modeled tick 49.2 seconds, no rolling-window waits.
- 300 ms per external service call: 99 ticks including five explicit rolling-window waits, 18,155 actual requests spread across permitted windows, maximum modeled tick 60 seconds.

These are full scheduled-wrapper measurements, distinct from the older manual-owner numbers above. They count mutable hint updates through the same meter. Their synthetic elapsed time includes the harness's fixed cadence and explicit waits; neither model is a live completion ETA or proof of Google runtime/quotas. The authenticated checkpoint shortcut removes repeated history-chain startup growth within the preserved absolute 4,096-checkpoint maintenance limit. Missing keys and legacy stores retain safe full recovery but do not inherit this modeled scheduled-throughput result.
