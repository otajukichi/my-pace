# Owner-controlled import runtime

Owner-run candidate, not deployed or live-accepted. Follow the combined release setup guide before normal use. No live Drive write, OAuth change, trigger, deployment, remote storage update or Git push has been performed by this work.

## What this kit does

This storage component supplies manual and owner-configured periodic Drive CSV import, plus the private durable backend. The combined app release includes separately tested authentication, app-domain and browser-sync modules; those still need the live setup/acceptance described in its main guide. Imported samples do not establish authoritative distance, pace or rewards. Source CSVs remain unmanaged and unchanged. A published imported run contains verified normalized samples and source/content provenance.

The source folder is fixed by ID in the code. Names of source folders and output folders never choose storage, and existing probe folders are never adopted. Bootstrap generates new private folder IDs and an anchor, persists them before creation, and resumes the same IDs after interruption. Do not delete or replace its configuration property to fix a failed bootstrap.

## Single setup, in the existing project

1. Open the same existing Apps Script editor/project whose owner already authorized Drive read access. Save a copy of its existing source and manifest. Preserve probe code, existing script properties and the standard Cloud project association. Creating a different script attached to the same Cloud project does not establish equivalent Drive-file access or consent.
2. In the combined release, add its complete `MyPaceComplete.gs` once. It already contains this runtime, owner functions and scheduled handler; do not also paste `FolderImport.gs`, `OwnerImportKit.gs` or individual module fragments. For an import-only standalone evaluation, `OwnerImportKit.gs` is the complete storage file. Preserve unrelated probe code and avoid duplicate function definitions.
3. Merge the supplied `appsscript.json` entries with the existing manifest; do not erase unrelated authorized dependencies/settings. Advanced Drive API v3 must be enabled for this existing project. Explicit scopes are `drive.file`, `drive.readonly`, `script.external_request`, and `userinfo.email`. The last supports fail-closed owner identity checking and can require additional consent. No full-Drive write scope is requested. Do not grant extra scopes merely because legacy probe code adds them implicitly.
4. The verified owner email is prefilled. Run `MyPaceImportBootstrap` yourself from the editor only when ready to create the private store. First execution pins the actual Script ID; subsequent executions enforce the same identity. Both active and effective user must match the owner. If owner identity is unavailable, stop; do not weaken the check.
5. Configure the owner-managed `MYPACE_WRITER_SECRET` in ScriptProperties according to the combined setup guide, matching the authenticated server secret. New stores reserve eight fixed IDs and use the secret for separately domain-separated checkpoint and discovery advice. No secret is generated or logged by this kit; do not put it in chat or source code. For an older pinned store, explicitly run `MyPaceRepairRecoveryConfiguration`, then `MyPaceRecoverStorage` until ready. The repair verifies and hash-binds the existing immutable anchor, adds only missing advisory IDs and preserves history. It never resets a store or silently installs credentials.
6. Run `MyPaceImportStart`, then `MyPaceImportResume` as needed. Each invocation has hard between-call limits and bounded work. `MyPaceImportStatus` reports durable progress and can finish mandatory interrupted checkpoint-index recovery; it is not guaranteed read-only. Respect `retryAt`; `budget-wait` means no new work was admitted. There is no automatic trigger creation. The combined app deployment is a separate explicit owner step in the main guide.
7. After coherent live acceptance, follow `OWNER-SCHEDULING.md` to create a Google UI time-driven trigger for `MyPaceImportScheduledTick` every fifteen minutes by default. Active work resumes; a completed sweep is rescanned hourly by default. Deleting that trigger in Google UI disables periodic execution. No trigger-installation scope is added.

Bootstrap and import are the owner-approved write actions. Loading code alone performs no network or storage action. Never expose the storage functions directly as an anonymous web API; only the combined signed dispatcher may serve app requests. Low-level exports are trusted server internals and must not be mapped directly onto caller-controlled IDs or commands.

## Results and failures

- `scanning` and `importing`: partial work remains. Resume manually or let the owner-enabled periodic handler continue.
- `retry`: temporary failure/backoff or bounded yield. It is not saved/completed. An invocation can exhaust its budget before persisting the error; `errorPersisted:false` means the prior durable cursor still governs a retry.
- `complete`: the current enumerated job sweep reached terminal states. It is not an atomic snapshot of the entire folder, so a later Start enumerates again. Duplicate candidates remain held rather than counted twice.
- `blocked`: inspect the safe error code. Missing MD5 is deliberately unsupported and fails closed; no timestamp/name identity fallback is implemented. Other malformed/unsupported sources can also stop the scan. Fix/review the cause and invoke `MyPaceImportRetryBlocked`, then Resume.
- `SCHEDULED_NO_PROGRESS`: three bounded attempts made no durable progress on the same import/finalization work. Pins remain intact. Review the cause, then use `MyPaceImportRetryBlocked` and manual Resume if needed.
- Changed, moved or missing unfinished sources pause with their pins and any previously committed history retained. Even a version-only change with the same checksum pauses an unfinished job conservatively. After review, `MyPaceImportRestartChangedSource` explicitly cancels that unfinished generation without deleting files or changing the original, returns idle, and allows a new Start. Unchanged content does not create an extra published run. A changed completed source stages a replacement and retains owner fields; conflicts fail closed.

## Accounting and limits

Each source step reads at most 1 MiB; legacy normalized outputs remain capped at 1,024 points; versioned packing v1 allows up to 4,096 stored points under the unchanged 256 KiB byte cap. Public route pages stay at most 1,024 points / 256 KiB, and checkpoints stay at most 2 MiB. Finalization verifies up to four source-range batches before one durable verification checkpoint; an interruption re-verifies the unfinished group. Per invocation, actual Advanced Drive and UrlFetch requests, including retries, are metered, with a 120-second between-call deadline and 2,000-request maximum. These checks cannot interrupt an already running Google call or prevent UrlFetch buffering a response. A bounded 8 MiB verified immutable protocol cache is trusted only during the same continuously held script lock, then discarded. Source, asset and write-parent privacy checks stay fresh. External edits/deletions of a cached protocol object may be observed only after the next lock acquisition; no stronger within-lock detection is claimed. The scheduler holds the script lock for its bounded invocation. Periodic checks use a short allowance; durable backlog can use up to 120 seconds. Interactive app writes use a short lock attempt and retryable BUSY, preserving the browser outbox. This is a visible background-processing tradeoff, not instant synchronization.

Before importing, Drive state durably reserves the full invocation allowance in rolling hourly buckets. The configured work-admission limits are 12,000 reserved calls and one hour of reserved runtime over a conservative 24–25-hour window. A hard interruption retains the full reservation. At a normal final/error update, the live request ceiling is first tightened to requests already spent plus at most 256 final-persistence requests. Only the excess above that enforced ceiling is refunded in the same durable update; an uncertain update leaves either the original full reservation or the smaller safe one. Runtime reservations are never refunded. This is conservative admission accounting, not a claim that all account requests or actual Google quota units are covered. Reads needed to recover the ledger, blocked/no-op/status invocations, bootstrap and explicit review actions consume requests before/outside an admitted work reservation. The editor wrapper meters the entire invocation, including bootstrap/configuration validation; returned usage includes those requests. Other scripts/apps and quota categories are not measured. Owner-enabled periodic retries respect the durable backoff and admission budget. No trigger is installed by this code and no paid quota expansion occurs. Scheduled closing-call reservation is 128 calls; the manual allowance remains 256. Per-admitted-work-tick quiescent checkpoints keep normal cold tails short; unchanged idle scans create no immutable history, while a hard interruption can still require bounded recovery.

## Remaining gates

- The final local suite, generated-bundle checks, independent reviews and model results are recorded in the combined release verification summary and `OWNER-SCHEDULING.md`; they are not live acceptance.
- Run the agreed coherent actual-folder import/interruption/restart acceptance bundle only after owner action. No real GAS throughput, complete-byte publication guarantee or actual quota behavior has been established by local mocks.
- Missing-checksum hash-first support and retention/garbage collection remain unimplemented. Authenticated INDEX recovery is incremental with no 4,096-checkpoint lifetime halt. Legacy configurations that exceed conservative recovery bounds require the explicit repair above. Retained storage and other per-object/catalog limits remain finite. Actual OAuth/deployment, browser migration, and save/reload/recovery acceptance remain owner-run gates; local app/auth code and tests do not establish them. No source data or coordinates are included in this package.

## Storage recovery

`recovering` / `WRITER_RECOVERY_PENDING` means authenticated bounded history discovery is still running. No partial or empty business snapshot is exposed; repeat the owner recovery step or let the configured tick retry. The app keeps its existing view and pending outbox. `WRITER_RECOVERY_SETUP_REQUIRED` requires the owner configuration repair, not repeated entity edits. An integrity/missing-authority error must be investigated without resetting data or deleting a valid hint witness. See `BOUNDED-INDEX-RECOVERY.md` and `MAINTENANCE-LIMIT.md`.

## Storage packing and public route pages

New jobs pin packing version 1: at most 4,096 points per immutable output, still at most 256 KiB. Existing jobs without that version retain 1,024-point packing and byte-identical pending reservations. Public route responses remain at most 1,024 points and 256 KiB, using signed within-output cursors. See `OUTPUT-PACKING.md` and `CURRENT-PERFORMANCE.md`.
