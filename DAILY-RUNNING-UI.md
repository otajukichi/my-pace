# Read-only daily running UI

The running screen has one 記録 tab and retains the existing date picker. It renders one compact `dailyRun` response containing all accepted segments, distance, average speed and recorded duration. It never requests CSV contents or source-point pages, and never derives CSV statistics or colors in the browser. Route fragments remain separate.

Manual running add/edit/delete, GPX upload, import/history/trend tabs, raw CSV preview dialogs and the home add-running shortcut have been removed. Previously stored manual/GPX entities are unchanged and remain in the existing global JSON export. Their values are not combined with prepared CSV totals. No record-database migration was added.

## Client state and cache

`src/lib/daily-running.js` uses a session-memory cache plus a separate disposable `mypace.daily-derived.v1` IndexedDB database, each bounded to 16 dates and 4 MiB of serialized prepared content. Keys bind the authenticated owner scope, store, dataset generation, schema version and date; ready payload hashes bind immutable content. Logout, owner or dataset changes clear the memory cache and invalidate pending responses. Persisted entries from another owner or dataset are ineligible for lookup. The existing record/outbox database and localStorage are not changed. A domain-separated opaque owner scope is returned only after authenticated login/session confirmation. Only then may the isolated cache be read using owner/store/dataset/schema/date keys. Cached data after reload is marked as saved data being revalidated; a known content hash revalidates it against the current endpoint. A local SHA-256 checksum detects accidental body corruption before reuse (it is not a server authenticity proof). Corruption, blocked storage and quota failures degrade to a live read without breaking the display. Other-owner entries are never read and are removed as the bounded cache is rewritten. Explicit logout closes the display, invalidates pending hydration and clears only this disposable derived database. Ordinary page close/reload retains the derived cache for a subsequent authenticated visit by the same owner. The original record/outbox/local legacy databases are untouched.

A newly selected uncached day shows loading. Ready days remain visible during a refresh, preparation of additional files, or transient fetch failure. Route geometry and all three statistics swap together only after a complete validated payload arrives. Failed preparation and failed fetches show distinct text and a retry. Only backend-confirmed empty responses show an empty day. A notModified response is accepted only against the same identity and content hash. Failed fetches do not create automatic render/retry loops.

The running date's current-day limit is computed with the 03:00 JST boundary independently of device timezone. Recorded duration formatting is presentation only; it is not moving-time calculation.

## Map

OpenStreetMap loads automatically. Optional GSI remains available. Map geometry and speed colors come from the prepared response. Every fragment gets start/end markers, and file/quality gaps are not connected. The renderer fits after the real canvas has nonzero dimensions, invalidates Leaflet size first, and uses modest relative padding. Multi-point routes have no artificial zoom-16 cap; a single point uses a useful finite neighborhood zoom. Advisory rerenders reuse the same owner/store/generation/date map node, preserving pan/zoom/provider; a new hash replaces its route layer without resetting a user-moved viewport; resizing invalidates size without repeatedly fitting. Tiles are independent of data readiness.

## Verification and limits

Focused synthetic tests cover Japanese date boundaries, stale navigation, canceled/evicted-date revisits, logout, scope isolation, unknown-identity binding, hash revalidation, bounded cache, atomic partial readiness, failures and removed UI paths. Map lifecycle doubles cover sizing, fit, fragments, colors, tile failure, provider changes, disposal, remount and antimeridian routes. These tests are not screenshots or native-browser interaction evidence.

Cold first-view target: two seconds excluding map tiles. The dedicated daily read begins once authentication is known, independently of legacy record/import synchronization. Neither an Apps Script cold request nor a Google login can be guaranteed to finish within this budget without deployed measurement. In-session cached date switching requires no network request within the one-minute freshness window. New-page cached display requires confirmed authentication and a matching locally known store/generation, then revalidates its hash in the background. No live site, trigger, import or account setting was changed for this implementation. Visual browser QA remains unverified in this environment because the available browser cannot reach the local container and installed Chromium execution is restricted.

Final affected-frontend verification on 2026-10-09: 216 tests passed, zero failures and zero skips across 15 focused files (daily cache/client, map/app integration, authentication lifecycle, migrated render/controller suites, legacy outbox, public information and build security). The public allowlist build completed with 47 assets. This is not the full repository aggregate or deployed visual/performance qualification.
