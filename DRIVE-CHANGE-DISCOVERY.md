# Drive change discovery: implementation and owner rollout

This candidate contains source code and synthetic tests only. No channel, deployment, trigger, credential, OAuth grant, import, or production setting was changed while implementing it.

## What runs

- `api/drive-changes.js` is a separate, normally disabled HTTPS receiver. Enablement is an explicit owner release step via `MYPACE_DRIVE_CHANGES_ENABLED=true` in the production server environment. Preview deployments reject it.
- The receiver authenticates the channel token using a domain-separated HMAC derived from the existing writer secret and store/channel IDs. The writer secret itself is never sent to Google or included in responses. No new secret or OAuth scope is required by this design.
- The receiver forwards only `driveChangeHint` through the existing signed server-to-GAS interface. Browser `api/sync` does not expose this action. GAS checks the authenticated bounded ScriptProperties registry for the registered channel ID, resource ID, expiration, token and message number, under the same script lock. The receipt path constructs no writer runtime and performs no Drive access. It coalesces bursts only when a durable pending hint already exists outside watched Drive. A generic hint never marks daily records as preparing. An additional bounded, best-effort per-process receiver rate limit returns 429; it never fabricates an acknowledged receipt.
- HTTP 204 is returned only after GAS returns an accepted durable receipt. There is no volatile background promise. Unknown registrations, recovery, transport errors and timeouts return failure; the retained cursor still catches missed notifications. Initial Google `sync` can race registration finalization and receive 503 safely.
- The existing owner scheduler is the only worker. An enabled discovery cursor replaces its old periodic full-folder scans. An idle preflight classifies at most 16 changes pages under cooperative 96-call/15-second limits before deciding whether Drive-backed work is needed. Its conservative full-profile quota reservation is persisted outside Drive, combined with the existing rolling totals under the same script lock, and settled to measured use once by reservation identity. A crash retains the charge. Classified work then shares the existing importer reservation: at most 16 discovery units under cooperative 96-call/15-second limits, then the importer and up to 16 daily preparation units with ten seconds of cooperative save headroom. All Drive Changes calls are metered under the same daily/rolling call and runtime budget. These are cooperative bounds: one Google service call cannot be interrupted midflight.
- When no hint arrives, changes-list reconciliation is due every 15 minutes. Notifications cover the entire account/shared-drive log, so a very large unrelated account backlog can still require several bounded preflights; this is a latency qualification limit, never a reason to display fake running preparation. Recommend exactly one owner-approved 5-minute trigger for the combined worker. Ordinary idle ticks before reconciliation is due perform no new work reservation or scan when completed state is unchanged. The old 60-minute full-scan default remains the legacy mode only.

## Durable discovery

Activation captures a Drive start page token before the initial recursive metadata crawl. The same queue handles baseline files, notification-driven deltas, and periodic deltas. A changes page containing source work and its queued IDs are committed atomically with the next authoritative cursor. An irrelevant-only page advances an authenticated advisory cursor in ScriptProperties, bound to the exact authoritative base cursor; losing that advisory progress only replays metadata. No source queue entry is skipped by an advisory advance. Folder pages likewise save queued children and pagination together. Draining registers work through the existing import store, then acknowledges the queue entry separately; a lost acknowledgement safely replays the same registration operation.

Notifications contain no file metadata and do not prove CSV completion. At drain time current metadata and ancestor membership are checked. Existing source version/checksum/range verification still applies before and after CSV reads. Changes to a logical file use the importer's existing source identity and replacement run. A changed unfinished generation is never silently cancelled or restarted; existing pin protections can block it for explicit owner review.

Only the fixed actual input folder and its descendants are accepted. The entire managed store tree, including metadata and assets, is excluded, including descendants. Shortcuts/native documents are not traversed. Ancestry is freshly checked, not persistently trusted. Moving a folder into the input subtree schedules a recursive metadata crawl; moving it out or deleting it retains already imported history. Known source or input-folder disappearance records a bounded provenance warning instead of deleting published records. The first 32 warnings are retained with an overflow indicator; source IDs remain internal.

Capacity is explicit: page size 32, 128 queued IDs, 128 tracked/queued folders, maximum ancestor depth 32, and discovery-state maximum 60,000 UTF-8 bytes. Backpressure drains queued work before fetching another page. Unsupported deep/large folder topology fails visibly; it is not reported as empty coverage. Backlogs, oversized files, API latency, quota waits or owner-review blocks can exceed the 30-minute save-to-ready goal. Synthetic tests are not live timing evidence. Measure ordinary and large cohorts and a complete day of quota usage before claiming that target.

## Self-notification quiescence

Classic Drive watches include the application's own state/output files. Persisting an empty-page cursor or notification hint back into Drive would create a new watched change indefinitely. This implementation deliberately keeps authenticated hint/replay state, irrelevant-only cursor/fallback timestamps, channel-registry mirror and preflight budget bookkeeping in one bounded ScriptProperties value outside Drive. The value is store-and-generation scoped and capped at 8,500 UTF-8 bytes, below the per-property limit. No new secret is introduced.

The scheduler classifies notifications before reserving Drive-backed work. Unrelated account CSV and managed-output/state changes neither create a source queue nor mark the daily head pending. After a genuine job finishes, its own remaining notifications drain using property writes only. A synthetic full-runtime test feeds every writer/output create back as a change and verifies no additional Drive writes after completion, including a later periodic fallback.

Pause first writes the disabled property barrier and then the Drive state. If the second commit fails, the scheduler refuses to resume from stale enabled Drive state. Activation publishes the Drive state before enabling the property mirror; an interrupted activation fails safe until an explicit owner retry. An authenticated enabled registry whose channel mirror update was interrupted is repaired from authoritative channel metadata without another watch registration. Corrupt/unverifiable property state fails closed and preserves the older authoritative cursor. Do not clear these state properties as a troubleshooting shortcut.

Do not edit the generated source to configure this setting, so subsequent full-source updates preserve it. Run `MyPaceDriveChangesActivate` from the owner editor. 5. Explicitly activate daily preparation using the daily owner entry point. Replace the old importer trigger with exactly one 5-minute `MyPaceImportScheduledTick` trigger after approval; do not add a parallel cron or a trigger per notification. Existing clock owner/store guards remain required.
6. Verify channel ready status, source-folder baseline completion, delta coverage, existing imported job state, source warnings, and daily publication. Verify one real small recording end-to-end only under approved live test scope. Check notification delivery and a deliberately missed notification through retained-cursor fallback. The module accepts an optional shared-drive ID for an explicitly selected shared-drive change log, but the source root remains fixed. Do not change the live source scope implicitly. This rollout uses classic Drive `changes.watch`, not the Workspace Events developer-preview recursive subscription API.

## Renewal and recovery

Channels request at most seven days and renew at least one day before expiry. Old and new channels overlap until expiration, and their message sequences are independent. Expired channels fail authentication. Renewal runs ahead of routine delta work so a periodic tick cannot starve it.

A registration intent is durably saved before calling Google. If Google registration succeeds but its response or final persistence is lost, the candidate does not blindly create another channel or invent a resource ID. Status reports `DRIVE_CHANGE_WATCH_UNRESOLVED`; cursor reconciliation continues. Review the pending registration. After its requested maximum expiry, the explicit owner function `MyPaceDriveChangesResolveExpiredWatch` can clear it, and the next tick registers a replacement. This function refuses to discard an unexpired ambiguous registration.

An explicitly rejected/expired changes cursor clears trustworthy coverage and reports `DRIVE_CHANGE_CURSOR_EXPIRED`; it does not silently skip changes. After owner review, `MyPaceDriveChangesResetExpiredCursor` captures a fresh cursor and recrawls source metadata while retaining existing imports, queued IDs and history. If the main scheduler separately entered a blocked state, use its existing owner retry flow after fixing the cause. Permission errors and unclassified failures are never interpreted as deletion.

## Rollback

Run `MyPaceDriveChangesPause` from the owner editor and disable the production receiver flag, then pause/restore the owner scheduler cadence as explicitly approved. Pause preserves cursor, queue, source evidence, imported records, daily generations and warning state. Its property-side pause barrier remains authoritative if the later Drive pause commit is interrupted; retry the explicit owner action rather than clearing state. Restoring to an isolated target must keep discovery disabled, clear inherited channel registrations, and never copy the original store/generation property namespace. Existing watch channels are not silently deleted; they expire naturally, and the disabled receiver returns failure. No trigger is automatically removed and no work resumes itself. Reactivation reuses the same saved scope and cursor. Restoring the previous application/UI release must not clear writer pins or delete daily data.
